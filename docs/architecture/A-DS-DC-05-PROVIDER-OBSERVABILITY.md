# A-DS-DC-05 · Диагностика отказов DeepSeek

CAL-INC-01 выявил отсутствие безопасной детализации причины у `provider_unknown`. Сохраняем существующий финансовый результат и дополняем каждую новую ошибку операции полем `provider_failure` в приватном ledger. Для D1 то же поле доступно в `context.provider_failure`. Исторические строки без поля читаются без миграции.

| Поле | Источник |
|---|---|
| `operation_kind` | Локальный тип upload, chat, status или delete |
| `failure_stage` | transport, http_status, response_read, json_decode, response_schema_validation, file_metadata_validation или financial_accounting |
| `exception_class`, `safe_reason_code` | Контролируемые локальные категории, включая connect/read/write/pool timeout, network/protocol и условия проверки метаданных |
| `http_status`, `response_received` | Статус из границы HTTP, если заголовки получены. Отсутствие наблюдённого ответа совместимо с начислением |
| `provider_error_code` | Только совпавшая с HTTP статусом документированная числовая категория из JSON `error.code`, иначе null. Публичный контракт не обещает такой envelope |
| `elapsed_ms` | Время операции по монотонным часам до диагностики, целые миллисекунды |
| `financial_outcome_unknown` | Истина при удержании из-за неопределённости или overage. Для прежнего ordinary upload 413 сохраняется документированное локальное исключение. Controlled CAL удерживает резерв и при 413 |

При проверке файла различаются отсутствие, неверный тип и несоответствие. Значения метаданных, текст исключения, заголовки, целые response bodies, реальные handles и данные пользователя не входят в `provider_failure`. Из необязательного error body читается ограниченный JSON. Нераспознанное содержимое отбрасывается. Нормализованные показатели usage и приватный черновик сохраняются после валидации контракта и usage. `reasoning_content` не сохраняется. Штатный приватный реестр bindings сохраняет handles успешных загрузок.

Диагностика не изменяет атомарного резервирования, запрета последующих платных операций при unknown, отмены незапущенных операций, идемпотентности, бюджета кампании и правил GO. HTTP-успех с непригодным ответом оставляет финансовый результат неопределённым. Для старых записей без поля и для обрыва процесса до создания диагностики первопричина остаётся неизвестна.

Фактический CAL-INC-01 требует сверки с провайдером. Разблокировка и повтор требуют отдельного архитектурного решения и GO. [Проект сверки](../runbooks/ds-dc-02/CAL-INC-01-RECOVERY-DRAFT.md)
