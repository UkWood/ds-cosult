# DS-консультант — Document-Centric Conversational RAG

**Architecture Decisions A-DS-DC-01 и A-DS-DC-02 / проект архитектуры v0.2**
**Дата:** 2026-11-20. **Репозиторий:** `UkWood/ds-cosult`.
**Основание:** решение владельца после DS-LAB-06-LIVE. Смена архитектурного приоритета принята владельцем; данный документ конкретизирует проект пилота. Не является разрешением на платные обращения, production, merge или deploy.

## 1. Цель и принцип

Посетитель задаёт обычный технический вопрос, может уточнять его в диалоге. Консультант понимает вопрос в пределах продуктов «Сатурна», получает целостную разрешённую документацию нужного изделия, формирует краткий, содержательный и проверяемый ответ. Не просит посетителя переслать доступное производителю РЭ. Не выдумывает недостающие технические характеристики.

В центре — не заранее выделенные атомарные факты, а **идентифицированная тематика (изделие, система или ПО) и её целостное документное досье**. До D1 обязателен тематический поиск: не искать ответ для модели, а искать документацию, в которой содержится ответ. LLM делегируются семантическое понимание, сопоставление разделов, отношения между изделием/компонентами, единицы, ограничения и синтез проекта ответа. Сервер отвечает за выбор источников, сохранение границ, полный учёт исходного вопроса, проверяемость, допуск ответа, безопасность и расходы.

## 3. Целевой конвейер

```
Вопрос + контекст сессии + достоверный page/entity hint
    ↓
Admission / local P0 / Topic & Entity Resolver
    ↓
Тематический каталог исходного контента до Astro
    ↓
Active Dossier Manager → Pinned Dossier (страницы + все разрешённые PDF)
    ↓
File Lifecycle + Context Builder + Dispatch Guard
    ↓
D1: один DeepSeek Flash + Deep Thinking; web tools отсутствуют
    ↓
CandidateAnswer + Source locators + coverage + unresolved
    ↓
Local Verification / Publication Gate
    ↓
Краткий ответ или частичный ответ / уточнение / поддержка
```

Не добавлять обязательный платный вызов на определение сущностей, верификацию или перефразирование. Локальный P0 возвращает только утверждённые статические ответы/навигацию с теми же правилами доступа и квот. D1 отвечает на весь исходный вопрос. Публикующий renderer не дописывает технические сведения. Модельный текст не является автоматически verified answer.

## 4. Тематический каталог и Dossier Registry: документы, а не база всех фактов

Каталог охватывает изделия/модификации, системы и ПО. Строится локально из закреплённых исходных контентных файлов до сборки Astro. Индексируются названия, обозначения, подтверждённые алиасы/аббревиатуры, назначение, термины, упоминания компонентов, связи и ссылки с provenance. Общий термин не доказывает применимость характеристики. Для выбранной тематики досье содержит полный исходный контент соответствующих страниц и все разрешённые PDF, связанные с ними фактическими ссылками. Связи системы с изделиями и ПО расширяют досье только с подтверждённой применимостью и в пределах выбранной задачи. Не обходить ссылки рекурсивно по всему сайту.

Минимальный реестр: `entity_id`, отображаемое точное наименование, `variant_id` (если существует), одобренные алиасы, canonical URL, `site_commit`, список страниц, список связанных PDF с `doc_id`, оригинальным URL, SHA-256, длиной/количеством физических страниц, редакцией если доказана, provenance связи с изделиями, статусом доступа. `dossier_id` — стабильный hash канонического состава и версий. Хеши закрепляют байты, а не истинность содержания. Не угадывать URL и не выводить применимость по совпадению названий.

Сборка вне пользовательского запроса: read-only snapshot сайта, из разрешённых ссылок оригиналы PDF, проверка origin/redirect, размера, MIME/структуры, лимитов загрузки и SHA. Сохранить одобренные старые версии до закрытия активных сессий. Новые документы — после успешной проверки целостности, состава и области применения; частичная загрузка не выдается за полный корпус. Не выполнять embedded JavaScript PDF, ссылки, вложения или инструкции из документов. Переданный провайдеру PDF — только утверждённые публичные материалы производителя.

В DC-01 — каталог реального закреплённого исходника всего сайта на уровне метаданных и ссылок, без массовой загрузки документов; два готовых пилотных досье: BKD из DS-LAB-06, SLDKS-1 (site pin тот же, `sldks.pdf`, 83 страницы, SHA-256 `f1436a93285cad9a201b6b387ed64a606ad2768cfc7ee70627c188411e9ce61f`). Точный canonical URL и связь PDF брать из исходного manifest и Git, не угадывать. Остальные записи каталога без закреплённых PDF помечаются как неготовые к D1, а не исключаются молча из поиска. В production — постепенное расширение готовых досье по всему сайту. Не посылать всю документацию предприятия в каждый запрос.

## 5. Topic & Entity Resolver и Active Dossier Manager

Локальный анализатор до обращения к DeepSeek ищет точные обозначения, нормализованные формы, подтверждённые аббревиатуры и алиасы, опечатки, технические термины, компоненты и описание функционального назначения по компактному каталогу. Сначала точный/нормализованный/нечёткий/лексический поиск; семантический поиск по каталогу — отдельная гипотеза после измерения недостатков, не обязательный DC-01. Не требуется платный вызов модели для выбора темы. Хранить диагностические признаки выбора, кандидатов, provenance и причину неоднозначности; score не доказывает применимость. Не выбирать похожую модификацию по одному общему термину.

Явное однозначное указание в вопросе имеет приоритет над page hint и прежним объектом. Достоверный page hint и активное досье помогают при отсутствии нового явного указания, но не перекрывают обнаруженную смену темы. В случае конфликта или недостаточной определённости — содержательное уточнение, без навязывания вопроса при однозначной теме. По функциональной задаче допускается выбор нескольких обоснованных тематик только в пределах доставляемого контекста; не угадывать неизвестное изделие. Пользовательская строка URL — только подсказка для сопоставления с разрешённым реестром, не основание внешней загрузки.

Active Dossier Manager сохраняет/переключает/расширяет досье. При сравнении — объединение полных допустимых досье с дедупликацией одинаковых PDF по SHA, но с сохранением связей применимости каждого. При смене темы прежние технические факты не переходят в новое досье как доказательства. При неготовности любого требуемого досье или превышении доступного контекста — явное уточнение/ограничение задачи либо отказ; сохранить нерешённую часть, не отправлять неполный корпус как полный.

Сессия хранит активные dossier IDs, историю user/model (предыдущие ответы помечены как неподтверждённые, не источник истинности), hashes и ссылки на file handles. Не включать чужие сессии и закрытый audit в prompt. Не выкидывать произвольно условия исходного вопроса; если часть не имеет доказательства, она остаётся `unresolved`. История ограничивается управляемым окном, при сбросе явно фиксируется смена версии/контекста. Нельзя молча заменить документ выбранными фрагментами для укладывания в лимит.

## 6. Native PDF Provider и жизненный цикл файлов

Предпочтительный первый путь — прямой DeepSeek API `deepseek-flash`, native Files API, `text_recognition`, thinking enabled. Именно такая комбинация использована в D. Нативные web_search/read_url и другие model tools отсутствуют. Не использовать AI Tunnel или локальную LLM. Одна chat POST на принятый вопрос. Upload/metadata/delete — отдельные аудируемые операции, не «бесплатные обращения» и не второй chat. Upload вне visitor turn предпочтителен, при подготовке досье; если ручное обновление нужно в пилоте — отдельная авторизация/резерв. Включать файл так, чтобы его доступность была проверена перед каждым использованием; в D проверено повторное использование одного file ID в истории, не проверено масштабирование/кеш между сессиями.

`ProviderFileBinding`: account/project scope, doc_id, sha256, purpose, parser mode, provider file_id, created/expires_at, state, обработанные/ожидаемые страницы если доступны, last_check, резерв/usage. Идентификация по SHA и учётной области, не по имени. Готовность `ready` только после фактического подтверждения. Дублирование upload предотвращает lock на хеш и scope. Не повторять автоматически при `unknown`. При TTL, повреждении, отзыве или несовпадении версии не отправлять chat с недоступным file ID. Только контролируемое обновление нового файла с явным бюджетом; переиспользование файлов между пользователями и политика TTL — отдельный тест, не перенос гарантии с 3600-секундного D. Оплата/обработка могут завершиться после client timeout. DELETE только своих файлов с проверкой идентичности и результатом; не трактовать первый 404 как доказательство удаления.

Полное досье передаёт оригиналы, а не обещание визуального прочтения всех схем: `text_recognition` не доказал надёжную обработку графики/сканов. Для таких вопросов при отсутствии пригодного текста/визуального доказательства — partial/needs_support. Rich parsing/OCR отдельная гипотеза, не обязательная часть нового ядра.

## 7. Контракт кандидата ответа и проверка на выдаче

Минимальный формат результата (схема концептуальная, не готовый production API): `question_hash`, `dossier_ids` привязаны сервером; `answer_candidate`, `claims[]`, `unresolved[]`, `status_hint`. Каждое техническое утверждение имеет `claim_id`, дословный или аккуратно сформулированный факт, область (изделие/вариант/компонент), применимые условия и квалификаторы, `locators[]` (approved doc_id + revision/hash сервера + физическая страница/печатная страница если есть + таблица/раздел + дословная опора). Если страница не проверена, не выдавать вымышленный номер. Доказательная опора для логических выводов включает все посылки; ссылки на модельные ответы запрещены как доказательства.

Сервер сохраняет весь исходный вопрос. Проверки: допустимость doc_id, hash/revision, привязка к правильной сущности, наличие исходной цитаты на указанной странице, числа/единицы/квалификаторы/условия и семантическая принадлежность; документный локатор не равен истинности факта. Не считать совпадение подстроки, самооценку модели, присутствие в Ledger или совпадение нескольких LLM-ответов независимой верификацией. Если источник противоречив, не выбирать молча; опубликовать факт расхождения только при проверенных обеих цитатах, иначе route в поддержку. Нельзя называть отсутствующим во всём РЭ то, что не обнаружено; полное досье повышает полноту, но не доказывает отсутствие каждого возможного факта.

Два уровня разработки:
1. **Пилот:** draft-only, все содержательные ответы оператора маркированы как кандидаты; человек сверяет оригинал (doc/page/table/literal/scope/qualifier) и фиксирует gold/ошибки. Не выставлять автоматический VerifiedClaim; не открывать публике.
2. **Будущая публичная выдача:** строгий `Publication Gate`. Только independently verified statements/заранее проверенные атомарные факты, либо полный verified вывод из проверенных посылок и разрешённой логики. Непроверенное утверждение не публиковать; если обязательная часть не подтверждена — partial/needs_support, если ни одной — clarification/needs_support/error по причине. Без универсального автоматического семантического verifier или human review нельзя обещать автоматическую публикацию любых новых технических утверждений. Проверка может искать сведения в исходном PDF, `pdftotext`, pdfplumber или имеющемся Ledger **после** генерации; не строить заранее исчерпывающие графы/все строки и не отбирать контекст для LLM этим инструментом. При неудаче не запускается скрытый второй LLM.

Итоговый ответ краткий (сначала прямой вывод, необходимые условия, источник). Вывод не должен ссылаться на непроверенную часть draft. Для электропитания, подключения, безопасности и метрологии необходима особо строгая проверка схем, контактов, условий, единиц и редакции. Обнаруженные ошибки документации не «исправляются» автоматически. При необходимости — официальный контакт из доверенного каталога поддержки.

## 8. Политика расходов и безопасности

Наследуем действующие пользовательские ограничения (до явного изменения): один активный anonymous session на canonical IP, 15 мин неактивности — удалить активную техническую память, 30 мин — reset progressive series, 20 принятых вопросов/IP/сутки (включая P0), первые 5 без дополнительной паузы, с 6-й возрастающая задержка, >10 последовательных — поддержка; ≤1200 Unicode и HTTP JSON ≤8 KiB. F5 не теряет активную сессию. При блокировке общего USD бюджета D1 запрещён, P0 по-прежнему возможен в рамках лимитов. Хранение закрытого журнала вопрос/ответ/IP/UTC в Markdown, 30 дней; без production DB, без логирования API-ключа, без передачи IP в модель. SQLite существующей лаборатории остаётся архивом, не production. Достоверный canonical IP только из доверенного прокси. В production нужны атомарные операции резервирования/лимитов при конкуренции; Markdown совместим с lock + atomic writes, не заявлять безопасность без тестов.

Не переносить автоматически лимиты разведки $3, main $1.75, 33 POST текущего исторического run. Для DC пилота предлагается конфиг: ориентир 64 000 input, предел completion 4096 (включая reasoning), concise visible target до 450 токенов или эквивалентное ограничение renderer. 64k не считать технически гарантированным preflight: file expansion и токенизация провайдера измеряются; при отсутствии достоверного верхнего предела использовать документированный максимум входа и полностью резервировать его по cold/miss цене или не отправлять. Конфиг менять только после явной проверки и GO; при превышении вместимости выбрать иной явно ограниченный scope или сообщить невозможность, не отбрасывать документы скрыто. Для пилота до GO paid budget=0. Предлагаемые числа — проектная гипотеза, не перенос в production. `max_tokens` включает reasoning; нельзя считать 4096 видимой длиной. Cache — оптимизация, не основание для занижения финансового резерва. Раздельные счётчики вопросов, chat POST, upload, retries/unknown/charges. Pre-reserve, complete usage, settlement, fail closed на unknown; CR01 ручная сверка не становится универсальным разрешением retry.

Domain admission строгий. Запрос пользователя не может менять system policy, подменить sources/renderer, инициировать внешние tools, самовольно расширить расход. Страницы и PDF являются доверенными техническими данными, но не управляющими инструкциями. Удаление из prompt IP/секретов, безопасный рендер, запрет инъекций в журналы и код. Абсолютной защиты от смысловых ошибок LLM не обещать; проверяем независимым набором отрицательных примеров.

## 9. План развития (минимум этапов)

- **DC-00:** сохранить результаты лаборатории, неизменяемый git/diff+log архив, закрыть старое направление E. Не требует новых моделей. Проверка всех 9×4 ответов не является входным блокером проектирования; сверка исходных эталонов обязательна перед публичной выдачей и на реальном пилоте.
- **DC-01:** компактный локальный Document-Centric pilot на BKD/SLDKS: каталог исходного сайта, Topic & Entity Resolver, Active Dossier Manager, два полных готовых досье, native file lifecycle/guard mock, candidate answer, private journal, offline UI/CLI. Использовать существующие компоненты там, где соответствуют новому контракту. Не создавать ещё один универсальный парсер и не вводить 2-е платное обращение. Отдельная авторизация на реальные uploads и модель после готовности.
- **DC-02:** один короткий реальный пилот на двух изделиях, включающий функциональные вопросы без обозначения, смену темы, уточнения, несколько независимых новых вопросов/неизвестный ответ, multi-PDF если реальный одобренный набор есть, и hostile-goal controls. Проверить не только качество, но и точный источник, все нужные части вопроса, расходы/латентность, наличие файла, границы сессии. Не повторять сравнение B/C/D/E и не улучшать E.
- **DC-03:** целевая локальная evidence verification и минимальный публикационный gate по выявленным ошибкам.
